# 因果预测与 Spot GPU 调度实施计划

> **供执行代理使用：** 必须按复选框逐项执行；实施时使用 `executing-plans`，先写失败测试、再写最小实现。所有修改只可发生在论文工作树 `D:\Users\Desktop\data_center_energy_optimization\.worktrees\paper-spot-gpu-stage1`，不得读取、导入、复制、修改或测试 `career` 命名空间。

**目标：** 建成可复现的单数据中心反事实实验：用 Alibaba 2026 Spot GPU trace 构造可调 GPU 负载，在四个固定的 ERCOT 2025 窗口中，以运行成本为首要目标，并在 1% 成本保护内改善 ERCO 系统风光时段匹配、降低 ERCO 消费侧碳强度。

**架构：** 能源输入层从可审计的 EIA 历史观测中按 48 小时信息保护期生成 90 日直接多步 Ridge 预测；它不再依赖 HSL 历史快照。算力层把 trace 规范为按 GPU 型号和 gang 请求的 HP/Spot 作业，并以配置化功率情景映射为设施增量功率。调度层每天只看到次日 DAM 价格和当天可得的预测，按成本、风光时段匹配、碳强度三层目标滚动求解；实际风光和碳只用于事后评价。

**技术栈：** Python 3.13、NumPy、pandas、PySCIPOpt、标准库 `unittest`、CSV/JSON、Markdown。当前环境没有 scikit-learn；Ridge 用 NumPy 线性代数实现，不新增依赖。

```python
coefficients = np.linalg.solve(x.T @ x + penalty, x.T @ y)
```

- [ ] **步骤 3：实现滚动调度和三级目标。**

按 `(gpu_model, gpu_count, release_hour, deadline_hour, required_run_hours)` 聚合整数 cohort；每小时的变量是可检查点的完整 gang 数，不允许连续 GPU 松弛。每日模型只优化未来 24 个交割小时，提交后只执行第一个日前块。实际 HP 到达时优先占用物理容量，Spot 可被抢占并携带剩余工作；核心期结束后不再接收新 Spot，171 小时闭合期仍结算已有任务的能耗、成本和未完成量。最终逐作业 EDF 恢复程序必须验证 release、deadline、GPU 型号和 gang 容量；无法恢复即报告具名不可行性，而非输出松弛结果。

每个日决策对每种 GPU 型号**按小时**保留 `max(已知在运行 HP 的衰减轨迹, 最近 336 个已实现 HP 小时的 0.95 分位)`，再按物理容量截断；不使用块起点单小时峰值覆盖整个 24 小时块。另按型号、按 deadline 增加累计未来容量约束：对每个截止时刻 `d`，要求当前块内 `deadline ≤ d` 的已排 gang·h 不少于“剩余 gang·h − 未来可排容量”，以阻止成本目标把工作无界后推。调度策略为：`fifo`（静态 EDF）、`reserve`（风险预留 EDF）、`price`（风险预留+DAM 成本）和 `proposed`（三级目标）。主策略依次求解：

```python
cost_star = solve_minimum_cost(model)
guard = 0.01 * max(abs(cost_star), 1.0)
fix_cost_upper_bound(model, cost_star + guard)
alignment_star = solve_maximum_alignment(model, forecast_renewable_index)
fix_alignment_lower_bound(model, alignment_star, tolerance=1e-6)
solve_minimum_carbon(model, forecast_consumed_carbon)
```

其中 `forecast_renewable_index[t] = (forecast_wind[t] + forecast_solar[t]) / max(positive_forecast_sum)`。报告的“时段匹配”是设施负载对这个**无量纲 ERCO 系统出力指数**的加权平均，不报告为本地可再生能源 MWh 消纳。`evaluation.py` 用同一冻结公式将预测换为实际 ERCO 风光，另以 `facility_mwh × 1000 × lbs_per_kwh × 0.45359237` 计算实际消费侧 CO2 kg；这两类实际信号不能进入调度输入。

## 诊断记录与调度修正

> 2026-08-18：执行 Task 3 冬季 pilot 时发现 GPU 侧可行性问题，并据此修正调度器。

### 诊断结论

- 四个 ERCOT 窗口重放的是同一份冻结 Alibaba core（相同 `spot_jobs`、`hp_jobs`、`capacities`、`core_start_hour`）；DAM 价格、风光、碳只进入目标函数，不进入任何约束，因此 **GPU 侧可行性在四个窗口完全相同**。冬季 pilot 的不可行同样会出现在春/夏/秋。
- 冬季 pilot 报出 31 个不可行块，具名原因分两类：
  1. `A800-SXM4-80GB` 与 `GPU-series-2` 的 HP 占用接近满容量（核心期 p95 分别约 154/176 与 785/976），风险预留后 Spot 容量过小；
  2. 多数块为块内 deadline 堆积（无单一型号总量超订），源于滚动 `required_now` 对未来容量过于乐观，导致作业延迟到最后一块。

### 修正方向

1. `_reserve_by_model` 改为**按小时**的预留：`max(已知在运行 HP 的衰减轨迹, 最近 336 小时 0.95 分位)`，不再用块起点单小时峰值覆盖整个 24 小时块。
2. `_solve_block` 增加**按型号、按 deadline 的累计未来容量约束**，阻止成本目标把工作无界后推。

### 待决

上述修正已落地且 `tests/paper/ercot_2025_spot_gpu/test_replay.py` 通过，但冬季 pilot 仍不可行，绑定约束仍是 A800/GPU-series-2 的 HP 近饱和：在严格“HP 绝对优先 + 风险预留”下，这两个型号留给 Spot 的容量本身很小。下一步需在 HP 建模上定夺：按设计公式的朴素 HP 占用（可超容量）还是按 FIFO 容量队列，以及是否对 A800/GPU-series-2 做单独处理或触发 `D_max` 回退。
